# 이슈 자동화 워크플로

입력: GitHub 이슈 번호 하나와 레포 이름 (예: `/issue 12 be` — 레포 이름이 없으면 아래 "시작하기 전에"가
먼저 묻는다. 그 이슈의 워크트리에 서 있으면 묻지 않는다). 부를 때 준 인자는 이 문서 끝에 `ARGUMENTS:` 줄로
붙는다. 이슈는 사람이 미리 작성해 둔다. CLAUDE.md의 규칙(아키텍처·코딩·Git·라벨)을 전제로 하고,
여기에는 이 워크플로에만 필요한 것을 적는다. "머지했어"를 받고 진입했다면 1~6단계를 건너뛰고
**7단계(머지 후처리)만** 따른다 — 그 전에 아래 "시작하기 전에"는 어느 경우든 먼저 한다.

이 스킬은 UOS-SE-TOUR/be(이 레포)의 사본이다. ClimPick 레포 limbing-aos 의 `/issue` 를 옮겨 와 이 레포에 맞췄고,
그 사본도 limbing-ios `/issue` 를 옮겨 온 것이다(aos #43). 규칙 대부분은 그 레포들에서 실제로 난 사고에서 나왔으므로
출처를 지우지 않고 남겨 둔다. 이 문서와 references·scripts·tests 에 나오는 `ios #번호`·`ai #번호`·`aos #번호` 는
ClimPick 의 limbing-ios·climpick-ai·limbing-aos 이슈·PR 이고 — 이 레포의 `#번호` 가 아니다 — 레포를 밝히지 않은
날짜 붙은 실측은 limbing-ios 에서, `aos 실측` 은 limbing-aos 에서 한 것이다. 이 레포에서 잰 것은 `be 실측` 처럼
레포를 붙여 적는다.

## 이 스킬의 파일

이 스킬의 디렉터리는 `${CLAUDE_SKILL_DIR}` 다. 이 문서와 references 파일에 나오는
`<스킬 디렉터리>` 는 전부 이 경로를 뜻한다. 이 문서는 불러올 때 그 자리가 절대경로로 채워지지만
references 는 Read 로 읽으므로 채워지지 않는다 — 여기서 본 값을 그대로 옮겨 쓴다. (위 경로가
절대경로가 아니라 달러·중괄호 변수 모양 그대로 보이면 치환이 안 된 것이니, 스킬을 불러올 때 함께
표시된 "Base directory for this skill" 경로를 쓴다.)

- `references/worktree.md` — 잔재 조사·이어받기·워크트리 제거 절차. **2단계에서 이 이슈의 잔재가
  잡혔을 때**, 6단계 재진입에서 재부착이나 등록 정리가 필요할 때(`find.sh` 가 `NONE`, 또는 `FOUND` 에
  `prunable`·`container out`), 그리고 7단계가 부를 때 Read 한다.
  잔재가 없는 정상 경로에서는 읽지 않는다.
- `references/merge-cleanup.md` — 7단계 머지 후처리. **"머지했어"를 받았을 때** Read 한다.
- `scripts/` — 판정 스크립트. **판정만 하고 아무것도 지우지 않는다.** 지우는 명령은 문서가 시키는
  대로 직접 친다. 인자·출력 키워드·종료 코드는 각 스크립트 머리말이 정본이다(앞머리에서 나는 3 은 아래
  "스크립트를 부르는 법").
- `tests/run.sh` — 스크립트와 문서의 테스트. `bash "<스킬 디렉터리>/tests/run.sh"`

**스크립트를 부르는 법:**
- `bash "<스킬 디렉터리>/scripts/<이름>.sh" <인자>` 를 **단순 명령 한 줄로** 친다. 반복문이나 명령
  치환 안에 넣으면 격리 세션의 명령 가드가 "검증할 수 없는 구문"으로 거부한다(실측). 값이 필요하면
  출력에서 옮겨 다음 명령에 넣는다. **경로에 변수를 끼우지도 않는다** — `S=…; bash "$S/x.sh"` 처럼
  변수를 낀 경로도 같은 가드가 거부한다(ios #357 머지 정리에서 실측). 스킬 디렉터리든 제거 절차가 떠 두는
  사본이든 절대경로 리터럴로 한 줄씩 친다.
- **stdout 첫 줄이 판정 키워드**이고, 문서는 키워드마다 갈래를 적어 둔다. 적혀 있지 않은 키워드가
  나오면 멈추고 출력을 그대로 보여준다.
- 경로를 내는 줄(`path`·`worktree`·`orphan`·`other-orphan`·`other`·`gone` …)은 경로에 셸이 건드리는 문자가
  있으면 **라벨 뒤에 `-escaped` 가 붙고** `%q` 표기로 나온다(`path-escaped`, `orphan-escaped` …). 브랜치를 내는
  `branch` 줄(`residue.sh` 의 줄과 레코드 블록의 줄)은 기준이 더 좁아서, 아래 "인자는 큰따옴표로 감싼다"의
  **명령에 넣을 수 없는 브랜치 이름**이면 `branch-escaped` 로 나온다. 그런 줄은
  어떤 라벨이든 **명령에 옮기지 않고** 사람에게 넘기며 최종 보고에 반드시 넣는다 — 라벨이 달라 갈래에서
  빠지면 아무도 안 보는 디렉터리나 브랜치가 남는다.
- **종료 코드가 0이 아니면 판정을 못 내린 것이다**(2 사용법, 3 환경 실패 — 레포 안에서 도는 스크립트를 레포
  밖에서 불렀다, git 실패 등). 판정으로 읽지 말고 멈추고 stderr 를 그대로 보여준다. (레포 안인지를 보는 세
  스크립트는 레포 밖을 키워드로 낸다 — 아래 "시작하기 전에".) 모든 판정 스크립트는 `lib.sh` 를 불러오는
  앞머리에서도 3 으로 멈춘다 — `lib.sh` 를 못 읽었거나, 스크립트와 버전이 어긋났거나, 부른 셸에서 물려받은
  함수를 지우지 못했을 때다(`lib.sh` 머리말). 스크립트 머리말의 3 설명은 이 셋을 빼고 그 스크립트에서만 나는
  원인을 적는다 — 이 셋 말고는 3 을 내지 않는 `inside.sh` 만 앞머리를 적는다.
- 스크립트는 **cwd 에서 git 을 부른다.** 뒤따르는 비가역 명령도 cwd 에서 치므로 판정과 실행이 같은
  레포를 본다. 레포 경로를 인자로 받아 `-C` 로 돌리지 않는 이유가 이것이다. (예외는 둘이다. `ignored-check.sh` 는
  보는 것이 지울 워크트리 안의 파일이라 인자로 받은 그 워크트리 안에서 부른다. 그 인자는 늘 제거 절차 0번 ③
  `find.sh` 가 이 레포의 등록 목록에서 낸 `path` 다. `skill-repo.sh` 는 넘긴 스킬 디렉터리에서
  부른다. 알아내려는 것이 이 스킬이 든 레포이고, 그 값은 옮길 자리와 `same-repo.sh` 의 인자로만 쓰여 지우는
  명령의 판정에는 들지 않는다.)

**인자는 큰따옴표로 감싼다.** `rm -rf "<경로>"` 처럼 — 공백이 있으면(`~/My Documents/…`, 사람이 만든
`실험 302` 같은 이름) 인자가 쪼개져 엉뚱한 것을 지우고도 `rm -rf` 는 0으로 끝난다. 아래 예시는
자리표시자를 보이려고 따옴표를 생략한 곳이 있으니, 실제로 칠 때는 붙인다.
**브랜치 이름(`<브랜치>`)도 늘 큰따옴표로 감싼다 — 이 문서와 references 의 `git`·`gh`·`bash` 명령 예시는 브랜치
자리를 모두 감싸 두었다**(`tests/run.sh` 가 검사한다 — 검사의 한계는 그 테스트 주석에 있다). git 은 브랜치 이름에
`;`·`|`·`&`·`(`·`<` 같은 셸 문자와 `$`·백틱·따옴표·한글을 허용해서(`git check-ref-format --branch` 실측, ai #33),
따옴표 없이 치면 그 뒤가 명령으로 실행된다. `$`·백틱은 큰따옴표 안에서도 확장되므로 감싸는 것만으로는 다 막지
못하고, `-` 로 시작하는 이름은 감싸도 옵션으로 읽힌다(`git branch` 로는 못 만들지만 push 로 들어온 원격 브랜치는
그럴 수 있다 — ai #33 실측). 그래서 **영숫자와 `._/+-` 밖의 문자가 들었거나 `-` 로 시작하는 이름을 "명령에 넣을
수 없는 브랜치 이름"이라 부르고, 명령에 넣지 않고 사람에게 넘긴다.** 판정 스크립트는 그런 이름을 `branch-escaped`
줄로 내고(위 "스크립트를 부르는 법"), `<브랜치>` 인자로 받으면 사용법 오류(rc 2)로 멈춘다. 다만 이 거절은 옮겨
온 `%q` 표기를 걸러 내는 마지막 확인일 뿐이다 — 같은 명령의 다른 인자(스냅숏 경로의 `<평탄화한 브랜치명>` 등)에
든 이름은 스크립트가 돌기 전에 셸이 펼친다. 그러니 이름은 명령을 치기 전에 가린다. 스크립트를 거치지 않고 받은
이름(`gh pr view` 의 `headRefName`, 사람의 답)도 같은 기준으로 본다. 이 스킬이 만드는 이름(`<타입>/<번호>-<영어
슬러그>`)에는 그런 문자가 생기지 않으니 걸리는 것은 남이 만든 브랜치다(climpick-ai 사본에서 옮겨 왔다 — ai #31
codex 지적, ai #33, ios #562).

**경로를 문자열로 비교하지 않는다.** 레포 경로에 한글이 들면(limbing-ios 본 체크아웃이 그렇다 — 이 레포는 클론
자리가 사람마다 달라 한글 폴더 아래에 둘 수 있다) git이 등록해 둔 경로와 셸이 내는 경로와 모델이 타이핑한 경로의 정규화
형태(NFC/NFD)가 섞인다(실측). 파일 접근은 괜찮다 — 이 볼륨은
정규화에 무관해서 어느 쪽으로 쳐도 같은 디렉터리가 열린다. 문제는 `=` 비교뿐이다. 그래서 **같은
워크트리인지는 브랜치 이름으로, 같은 경로인지는 스크립트로** 가린다(스크립트는 NFC 로 맞추거나 `-ef`
로 비교한다). 경로가 명령에 필요하면 git 이나 스크립트 출력에서 그대로 옮긴다.

## 시작하기 전에 — 이 스킬의 레포 안에 서 있는지

1단계의 `gh issue view` 부터 이 워크플로의 명령은 모두 지금 작업 디렉터리의 레포를 본다. 그런데 세션은
`/Users/yschoi` 에서 열리기도 하고, 한 세션이 `/issue` 사본이 있는 여러 레포(이 레포와 ClimPick 의 limbing-ios·
limbing-aos·climpick-ai)를 오가기도 한다. 이 레포들은 같은 번호 체계와 브랜치 이름 규약을 쓰므로, 그대로 시작하면 레포를
못 찾거나 **다른 레포의 같은 번호**를 읽고 지운다(ios #655). 그래서 **사람이 이 워크플로를 시킬 때마다** 먼저 본다 — `/issue <번호>` 를 부를 때도, 같은
대화에서 "머지했어"라고 말만 할 때도 그 요청의 처음에 다시 한다. 앞선 요청에서 한 확인은 치지 않는다 — 그 뒤
작업 디렉터리가 다른 레포로 옮겨 갔을 수 있다.

**먼저 `<스킬 디렉터리>` 를 명령에 넣어도 되는지 눈으로 본다.** 경로에 `$`·백틱·`"`·`\`·`'`·개행·제어 문자가 있으면 큰따옴표
안에서도 셸이 먼저 펼쳐 엉뚱한 명령이 돈다(판정 스크립트가 `-escaped` 줄로 거르는 기준과 같다). 그런 경로면 어떤
명령에도 넣지 않고 멈추고 보고한다. 그다음 이 스킬이 든 레포의 본 체크아웃(`<스킬 레포 루트>`)을 구한다:

```
bash "<스킬 디렉터리>/scripts/skill-repo.sh" "<스킬 디렉터리>"
```

스킬 디렉터리에서 git 에 공유 `.git` 을 물어 구하므로, 워크트리를 `.claude/worktrees/` 밖에 두었거나 링크를 거친
경로여도 본 체크아웃이 나온다(경로 문자열을 잘라 구하면 그런 자리에서 연결 워크트리 자체가 나와 멈췄다 — ai PR #82
코덱스 지적).
- `FOUND` — 다음 `path` 줄이 `<스킬 레포 루트>` 다. `path-escaped` 줄이면 위와 같은 이유로 멈추고 보고한다.
- 스킬 디렉터리가 지워졌다 — `skill-repo.sh` 가 그 안에 있으니 대개 bash 가 `No such file`(종료 코드 127)로
  알리고, `<사본>` 의 스크립트로 불렀으면 `GONE` 이 나온다. 같은 대화의 앞선 머지 정리가 스킬을 불러온 그
  워크트리를 지운 경우다. 그 정리가 구해 둔 `<스킬 레포 루트>` 가 있으면 그대로 쓴다 — 지워진 것은 워크트리이고
  레포는 그대로다. 이 뒤 스크립트는 그 정리가 떠 둔 `<사본>` 의 것으로 부른다(`references/worktree.md` 제거 절차
  앞머리). 앞선 루트가 없으면 멈추고 보고한다.
- `NOT_IN_REPO` — 스킬 디렉터리가 레포 안이 아니다. 멈추고 보고한다.

그 값으로 지금 작업 디렉터리가 이 스킬의 레포 안인지 본다:

```
bash "<스킬 디렉터리>/scripts/same-repo.sh" "<스킬 레포 루트>"
```

- `SAME_REPO` — 아래 "어느 레포 작업인지"대로 확인한다. 이 레포 안에 서 있다는 것만으로는 이 레포 작업이라는
  근거가 아니다(그 자리가 아래 "이슈 워크트리"일 때만 근거가 된다). 이 스킬의 레포 작업이면:
  - 묻지 않고 이 스킬의 레포 작업으로 정해졌으면(요청이 이 레포를 밝혔거나, 아래 "이슈 워크트리"로 정해졌다)
    1단계로(7단계로 들어왔으면 7단계로) 간다. 번호 없는 "머지했어"는 이 레포 이름을 붙였어도 아래 "이슈 워크트리"에서
    7단계에 넘길 번호부터 정한다.
  - 물어서 답으로 받았으면 위 `same-repo.sh` 부터 다시 돈다(`<스킬 레포 루트>` 는 앞서 구한 값을 쓴다). 받은 답은
    그 요청이 이 레포를 밝힌 것으로, 답에 번호가 있으면 그 번호도 받은 것으로 쳐서, 다시 돌 때는 묻지 않고 판정대로
    간다 — 아래 "이슈 워크트리"를 다시 거치지 않는다. 묻고 기다리는 사이 세션이
    내려갔다 다시 열리면 작업 디렉터리가 이 레포 밖일 수 있는데(다시 열리는 자리는 마지막으로 서 있던 곳이 아닐 수
    있다 — ai #79 첫·셋째 코멘트), 이 갈래에는 옮기기 4.처럼 자리를 확인하는 단계가 없어서다. 답을 받자마자 옮기기 3.·4.(`cd` 와 그 뒤 확인)로 보내지 않는 것은, 이
    레포의 워크트리에 격리된 세션도 `SAME_REPO` 로 여기 오는데 그 세션은 `cd` 할 수 없어서다(옮기기 1.의 `ISOLATED`).
- `OTHER_REPO`·`NOT_IN_REPO` — 이 스킬의 레포 밖에 서 있다. 아래 "옮기기"대로 한다.
- `CWD_GONE` — 시작하기 전부터 작업 디렉터리가 없다. 지워진 워크트리 안에서 열렸거나 격리돼 있던 세션이라
  옮기지 않고 멈추고 보고한다.
- 이 절의 판정 스크립트(`skill-repo.sh`·`same-repo.sh`·아래 `branch-issue.sh`·`isolation-check.sh`) 어느 것이든
  종료 코드가 0 이 아니면 멈추고 그 출력을 보여 준다. 예외는 위 `skill-repo.sh` 의 127 하나다 — 다른 스크립트가 127 을 내면 판정을
  못 받은 것이니 멈춘다. `same-repo.sh` 의 2 는 인자가 비었거나 `<스킬 레포 루트>/.git` 디렉터리가 없다는 뜻이다 —
  `skill-repo.sh` 의 `path` 줄을 그대로 옮겼는지 본다(`branch-issue.sh` 의 2 도 같고, 이슈 번호가 1 이상의 정수가
  아니어도 낸다). 네 스크립트는 git 이 "레포가 아니다" 밖의 이유로 실패해도
  (지워진 등록을 가리키는 `.git` 파일, 소유권 문제 등) 3 을 낸다 — 레포 밖은 `NOT_IN_REPO`·`MOVABLE`·`NONE` 으로 낸다. 3 의
  이유는 stderr 로 가린다. `same-repo.sh`·`isolation-check.sh`·`branch-issue.sh` 의 stderr 에 `git 오류(레포 밖이 아니다)` 가 있으면
  지금 작업 디렉터리의 git 이 깨진 것이니 옮기지 않는다 — 등록이 지워진 채 남은 워크트리 폴더(그 `.git` 파일이 없는
  등록을 가리킨다)이거나 소유권 문제이고, 앞의 것이면 격리돼 있을 수 있다. stderr 와 함께, 아래 옮기기 1.의
  `ISOLATED` 처럼 그 레포의 본 체크아웃에서 새 세션을 열어 레포 이름을 붙여 불러 달라고 안내한다. `skill-repo.sh` 의
  같은 문구는 스킬 디렉터리 쪽 git 이 깨졌다는 뜻이니 그대로 멈추고 보고한다.

**어느 레포 작업인지** — 이 레포와 ClimPick 레포들에 같은 번호가 있고, 하네스가 고른 스킬이 사람이 뜻한 레포라는
보장이 없다. 이 레포 안에 서 있어도(`SAME_REPO`) 마찬가지다. 한 세션이 앞선 요청에서 이 레포로 옮겨 온 뒤 다른 레포의
번호만 받으면, 하네스는 지금 레포의 스킬을 고르기 쉽고 그대로 가면 이 레포의 같은 번호를 읽는다(ai #98·ios #659). 그래서
**사람이 그 요청에서 레포를 분명히 밝혔을 때**와 **그 요청이 지금 서 있는 이슈 워크트리의 작업일 때**(아래 "이슈
워크트리")만 묻지 않는다. 이 레포를 밝힌 말은 이 스킬을 부를 때 인자로 준 레포 이름(`/issue 12 be` 의 `be`, 대소문자와
상관없이), 레포 전체 이름 `UOS-SE-TOUR/be`, 이 레포의 이슈·PR 링크(`github.com/UOS-SE-TOUR/be/issues/…`·`…/pull/…`)
꼴로 온다. **번호 바로 앞에 붙인 `be`(`be #12`·`be 12`·`be PR #3`·`be 이슈 12` 꼴)는 이 레포를 밝힌 말로 치지 않는다** —
사람이 ClimPick 서버 레포(limbing-be)의 이슈·PR 도 늘 `be #315`·`be #341` 처럼 불러 와서, 그 꼴만으로는 어느 레포인지
가려지지 않는다(be PR #2 리뷰). 그 꼴이 오면 아래대로 묻는다. 다른 레포를 밝힌 말은 이런 꼴이다 — 레포
이름(`limbing-ios`·`limbing-aos`·`climpick-ai`, 옛 이름 `limbing-ai` 는 `climpick-ai` 다), 번호 바로 앞에 붙인
`ios`·`aos`·`ai`(`ios 659`·`iOS#659`·`aos #43`·`ai98`·`ai PR #12`·`ios 이슈 659` 꼴. `ios` 는 `limbing-ios`, `aos` 는
`limbing-aos`, `ai` 는 `climpick-ai` 다), 그 레포의 이슈·PR 링크(옛 이름 링크도). 이름은 낱말 그대로 견준다 —
`limbing-be`(ClimPick 서버 레포)에 든 `be` 는 `be` 가 아니고, `limbing-ai-pose` 같은 다른 레포가 따로 있어서
`limbing-ai-pose` 에 든 `limbing-ai` 는 `limbing-ai` 가 아니다. 할 일의 레포를 가리키지 않는 자리에 든
이름도 치지 않는다 — 경로(`…/be/src/…`·`…/AI/limbing-ai/scratchpad/…`), 짝 이슈 언급 같은 것이다.
**조금이라도 애매하면 묻는다** — 처음 보는 레포 이름이거나, `be`·`ios`·`aos`·`ai` 가 번호와 떨어져 레포가 아니라 주제를
말한 것일 수 있을 때(`/issue 12 BE 연동` — BE 는 백엔드를 두루 가리키는 말로도 쓴다. 영어 문장 속 be 동사도 레포
이름이 아니다), 번호 바로 앞에 `be` 를 붙여 말했을 때(위 — ClimPick 서버 limbing-be 일 수 있다) 등이다. 묻는 값은 왕복 한 번이지만, 잘못 읽으면 엉뚱한 이슈를 구현하거나 헛되이
멈춘다. 지금 서 있는 레포, 이 대화에서 앞서 다룬 레포, 하네스가 고른 스킬(레포 경로가 붙은 이름으로
보여도 — 사람이 그 이름을 골랐는지 하네스가 골랐는지 가려지지 않는다)은 근거로 치지 않는다 — 이 레포 안에 서 있다는 것은 아래 "이슈 워크트리"일 때만 근거가 된다. 세션이 레포를 옮겨
다닌 뒤에는 셋 다 사람이 뜻한 레포와 갈릴 수 있고, 앞선 대화는 요약되면 사라진다. 그래서 이 스킬이 멈추며 다시
불러 달라거나 새 세션을 열어 달라고 할 때는(이 절 밖의 멈춤도) 레포 이름을 붙여 부르라고 함께 적는다 — 붙이지
않으면 그 요청에서 다시 묻는다.
- 이 스킬의 레포 작업이면(요청이 밝혔거나, 이슈 워크트리로 정해졌거나, 그렇다는 답) 같은 질문을 다시 하지 않고, 이 확인을 부른 자리(위
  `SAME_REPO` 갈래나 아래 옮기기 2.)로 돌아가 이어 간다.
- 다른 레포 작업이면(요청이 밝혔거나 그렇다는 답) 옮기지 않고 멈춘다(사본마다 레포 사정이 달라 이 스킬의 문서를 그
  레포에 쓰지 않는다). 이때 "이 세션에서 `/issue` 를 다시 불러 달라"고만 하면 하네스가 이 레포의 스킬을 또 골라
  같은 질문이 되풀이될 수 있다. 그러니 그 레포 본 체크아웃에서 새 세션을 열어 달라고 안내한다. 스킬 목록에 그 레포
  경로가 붙은 이름(`<그 레포 경로>:issue` 꼴)이 보이면 그 이름으로 불러도 된다고 덧붙인다 — 그런 이름은 세션이 연
  자리 아래의 스킬에만 붙어 늘 있지는 않다. 어느 쪽이든 레포 이름을 붙여 부르게 한다 — 경로가 붙은 이름만으로는
  위에서 근거로 치지 않아 그 스킬이 다시 묻는다. 요청에 앞선 세션의 꼬리("앞선 세션이 remove 까지 했고 사후 확인은
  못 했다. 스냅숏 …, 대상 …")가 딸려 왔으면 부를 문구에 그 꼬리도 그대로 옮겨 적는다 — 빠지면 새 세션이 그
  `remove` 의 사후 확인을 건너뛴다(`references/worktree.md` "먼저 알아 둘 것"의 "앞선 세션의 꼬리"). 다만 그 레포가
  `/issue` 사본이 있는 레포(ClimPick 의 limbing-ios·limbing-aos·climpick-ai)가 아니면 — limbing-be·UOS-SE-TOUR/docs
  처럼 이 스킬이 없는 레포라는 답을 받은 경우다 — 위 안내는 따를 수 없으니, 대신 이 워크플로로는 할 수 없다고 알리고 멈춘다.

**이슈 워크트리** — 레포를 가리킬 수 있는 말이 하나도 없는 요청과, 이 레포 이름만 붙인 번호 없는 "머지했어"
(`머지했어 be`)는 아래 항목대로 한다. 그 가운데 `/issue <번호>` 와 번호 없는 "머지했어"는 지금 서 있는
자리를 본다. 뒤에 "이어서 해줘"·"ㄱㄱ" 같은 지시만 붙어도 같다. 이 스킬은 이슈마다 연결 워크트리를 만들고 브랜치 이름에 이슈 번호를 넣으므로(1·2단계),
그 워크트리에 서 있다는 것은 그 이슈를 작업하던 세션이라는 근거가 된다(ai #137). 그 밖에 레포를 가리킬 수 있는
말이 든 요청은 이 문단으로 오지 않는다 — 다른 레포를 밝혔으면 다른 레포 작업이고, 애매하면(`/issue 98 ai`,
`/issue 98 (짝 ios #659도)`) 위대로 묻는다. 서 있는 자리는 말이 아니라 git
상태라서 스크립트로 가린다 — 경로를 문자열로 견주면 한글 정규화에 걸리고, 본 체크아웃이 우연히 그 이름의 브랜치에
있거나 다른 레포의 워크트리에 서 있는 경우를 가려야 한다:

```
bash "<스킬 디렉터리>/scripts/branch-issue.sh" "<스킬 레포 루트>" <이슈번호>
```

- **`/issue <번호>`**(`/issue 137 이어서 해줘` 도) — 그 번호를 숫자만 넘긴다(`#98`·`98번` 이면 `98`). 1 이상의 정수로 읽히지 않으면(`098`
  등) 부르지 않고 묻는다 — 스크립트가 사용법 오류로 멈춘다. `SAME` 이면 묻지 않고 이 스킬의 레포 작업으로 간다 — 그 이슈의 워크트리에서
  작업을 이어 하는 경우다. `DIFFERENT`·`NONE` 이면 받은 번호가 어느 레포의 이슈인지 묻는다.
- **번호 없는 "머지했어"**(이 레포 이름만 붙인 `머지했어 <레포 이름>` 도) — 번호 없이 부른다. `FOUND` 면 묻지 않고 다음
  줄 `issue` 의 번호를 7단계에 이슈 번호로 넘긴다 — PR 을 막 올린 세션이 그 워크트리에 선 채 받는 흔한 흐름이고, 다른
  PR 을 뜻하면 사람이 그렇게 말한다(ai #137 에서 정함). 그 브랜치의 PR 이 아직 머지 전이면 7단계가 머지된 PR 을
  찾지 못해 지우지 않고 묻는다(`references/merge-cleanup.md` "대상 브랜치와 이슈 번호를 특정한다"). `NONE` 이면 어느 레포의
  몇 번 PR 인지(이 레포 이름을 붙였으면 몇 번 PR 인지) 한 질문으로 함께 묻는다. 답의 번호는 7단계에 PR 번호로 넘긴다
  (이슈 번호라고 밝혀 답했으면 이슈 번호로) — 따로 물으면 7단계가 대상을 또 묻고, PR 번호를 이슈 번호로 넘기면 7단계가
  다른 이슈의 고아를 잡는다(`references/merge-cleanup.md` "대상 브랜치와 이슈 번호를 특정한다").
- **번호를 받은 "머지했어"**(`머지했어 PR #127`·`머지했어 #127`·`머지했어 이슈 98`) — 부르지 않고 어느 레포인지
  묻는다. 그 번호가 PR 번호인지 이슈 번호인지 밝히지 않았으면 그것도 한 질문으로 함께 묻는다 — 7단계는 둘을 달리
  쓴다(`references/merge-cleanup.md` "대상 브랜치와 이슈 번호를 특정한다"). PR 번호는 브랜치의 이슈 번호와 맞춰 볼 수
  없어서 부르지 않는다.
- **번호 없는 `/issue`** — 부르지 않고 어느 레포의 몇 번 이슈인지 묻는다. 서 있는 이슈 워크트리의 번호로 대신하지
  않는다 — `/issue` 는 번호를 받아 그 이슈를 읽는 명령이다.
- **그 밖의 요청** — 부르지 않고 묻는다.

`branch-issue.sh` 가 `CWD_GONE` 이면 위 `CWD_GONE` 갈래대로 멈추고 보고한다. 종료 코드가 0 이 아니면 위 판정 스크립트
항목대로 멈춘다. 묻지 않고 정해졌거나 물어서 답을 받았으면 위 "어느 레포 작업인지"의 두 갈래대로 이어 간다.

**옮기기** — 격리되지 않은 세션에서 Bash 로 `cd` 하면 하네스가 세션의 작업 디렉터리를 그 자리로 옮기고
(`Primary working directory: <새 경로> (was <옛 경로>)` 로 알린다) 그 뒤 Bash 는 모두 거기서 돈다(2026-10-02
실측, ios #655 — 두 레포를 다 품은 `/Users/yschoi` 에서 연 한 세션이 이렇게 일곱 번 오갔다. 세션을 연 자리 밖으로
옮기는 것은 재 보지 않았다 — 하네스가 되돌리면 아래 4.의 확인이 어긋나 멈춘다). 그러니 새 세션을 열지 않고
옮겨서 이어 간다:
1. **옮길 수 있는 세션인지 본다** — 사람에게 묻기 전에 본다. 격리된 세션이면 답과 상관없이 멈추므로, 먼저 물으면
   질문 한 번이 헛돈다(ios #658):

   ```
   bash "<스킬 디렉터리>/scripts/isolation-check.sh"
   ```

   - `MOVABLE` — 어느 레포의 워크트리 안도 아니다. 2.로.
   - `ISOLATED` — 어느 레포의 워크트리 안에 서 있다(`reason` 줄이 경로로 걸렸는지, 연결 워크트리로 걸렸는지
     알린다). 격리된 세션으로 보고 옮기지 않고 `reason` 줄과 함께 멈추고 보고한다. 이 세션에서는 옮길 수 없으니,
     어느 레포 작업이든 그 레포의 본 체크아웃에서 새 세션을 열어 레포 이름을 붙여 불러 달라고 안내한다 — 어느
     레포인지는 사람이 안다.
     격리된 세션에서는 명령 가드가 `cd … && git …` 을 거부하고, 하네스가 작업 디렉터리를 워크트리로 잡고 있어
     옮겼다고 믿고 친 명령이 엉뚱한 곳에서 돈다(`references/worktree.md` "먼저 알아 둘 것").
   - `CWD_GONE` — 위 `same-repo.sh` 의 `CWD_GONE` 과 같이 멈추고 보고한다.
2. **어느 레포 작업인지 확인한다** — 위 "어느 레포 작업인지"대로. 이 스킬의 레포 작업이면 3.으로 간다. 그것을
   물어 답으로 받았어도 다시 판정하지 않고 3.으로 간다 — 기다리는 사이 세션이 워크트리에 격리됐으면 `cd` 가
   되돌려져 4.의 확인이 어긋나 멈추고, 그 밖의 변화(작업 디렉터리가 다른 자리로 옮겨진 것 등)는 3.의 `cd` 가
   절대경로로 옮겨 그대로 이어 간다.
3. `cd "<스킬 레포 루트>"` 를 **단독 명령으로 한 번** 친다. 판정 스크립트나 다른 명령과 한 줄에 묶지 않는다 —
   옮겨졌는지 확인하기 전에 그 명령이 돈다.
4. **옮긴 뒤 확인한다.** 다음 명령에서 레포 루트를 다시 구하고(2단계 첫 항목의 한 줄), 그 출력을 옮겨
   `test . -ef "<스킬 레포 루트>" && test "<다시 구한 루트>" -ef "<스킬 레포 루트>" && echo ok` 를 친다 — 지금
   자리와 그 레포의 본 체크아웃이 둘 다 옮긴 대상인지 본다. 경로는 문자열로 견주지 않는다(위 "경로를 문자열로
   비교하지 않는다"). `ok` 면 그 레포의 `CLAUDE.md` 를 Read 한 뒤 1단계로(7단계로 들어왔으면 7단계로) 간다
   — 세션을 연 자리가 레포 밖이었으면 하네스가 그 파일을 읽어 두지 않았을 수 있고, 라벨·커밋 규칙과 AI 표기 금지가
   거기 있다. 아니면 멈추고 본 체크아웃 안에서 레포 이름을 붙여 다시 불러 달라고 요청한다.

**`cd` 를 쳤으면 그 요청의 보고에 적는다** — "작업 디렉터리를 `<스킬 레포 루트>` 로 옮겼다". 4.의 확인이
어긋났으면 "옮기려 했지만 옮겨졌는지 확인하지 못했다"고 적는다. 세션의 작업 디렉터리는 스킬이 끝난 뒤에도 옮긴 레포에 남아,
그 뒤 시키는 다른 일(스킬 밖의 명령)이 그 레포에서 돈다(ios #658).
끝까지 갔든 중간에 멈췄든 같다 — 6단계 "종료"의 보고, 7단계(`references/merge-cleanup.md`)를 마치고 하는 보고,
그리고 4.의 확인이 어긋났거나 뒤 단계에서 멈추며 하는 보고 모두다.

이 확인을 지난 뒤 제거 절차에서 레포 밖에 서게 되면(0번 ①, 3번 "안에서 지웠을 때 나가기" 2.) 옮기지 않고 그
자리에 적힌 대로 멈춘다.

## 1. 이슈 파악

- 한 번에 다 받는다:

  ```
  gh issue view <번호> --json title,body,labels,milestone,comments
  ```

  라벨명과 마일스톤 제목이 5단계의 `--label`·`--milestone` 에 바로 넣을 수 있는
  구조로 온다. (사람용 출력을 쓰면 `--comments` 를 붙였을 때 파이프에서 본문·라벨·
  마일스톤이 빠지는 함정이 있어, 두 번 부르고 머릿속에서 합쳐야 한다. `--json` 이면
  그 함정이 없다.)
- **코멘트에 조사나 논의가 있으면 그것을 우선 근거로 삼는다.** 사전 조사 결과를 이슈
  코멘트로 남기는 일이 실제로 있으므로(원인 분석·수정 방향·재현 조건·제약), 안 읽으면
  그 조사를 못 보고 같은 분석을 처음부터 다시 하게 된다. 본문은 처음 관측이고,
  코멘트가 나중에 실측으로 바로잡은 경우가 많다 — 둘이 어긋나면 코멘트가 이긴다.
- 브랜치 이름은 **`<타입>/<이슈번호>-<기능>`** (예: `fix/268-hold-color`) —
  CLAUDE.md의 `<타입>/<기능>` 형식을 이 워크플로에 한해 이슈 번호로 좁힌 것이다.
  `<기능>`은 영어 소문자 슬러그로 짓는다 (한글은 경로·판별식에서 정규화 문제를
  만든다). 번호가 이름에 박혀 있어야 잔재 탐지·후처리가 정확히 대상을 특정한다.
  타입은 이슈의 타입 라벨, 탐색 범위는 `area:` 라벨(이 레포는 모듈 패키지와 같다)로 정한다(area가 없으면 본문·
  코멘트가 가리키는 코드에서, 여러 개면 모두를 범위로 잡는다 — 여러 개는 아래 라벨 확인에서 어긋남이라 먼저 묻고,
  "그대로 진행"을 받았을 때만 이 경우가 된다).
  **이어받는 브랜치의 슬러그는 새로 짓지 않는다** — 이미 있는 이름이 규약에 맞으면
  그대로 쓴다 (`references/worktree.md` 이어받기 6번).
- **라벨은 이슈에 반영된 값만 쓴다.** 세션이 "이 이슈 라벨이 틀렸다"고 판단하는 것은
  인정하지만, 그 판단은 이슈 라벨을 고쳐 반영한다 — 세션 안에만 들고 가면 5단계 PR
  라벨, 기존 PR 갱신, 재개한 실행이 이슈와 어긋난다(ios #475). 그래서 작업을 시작하기 전에
  이슈 라벨이 CLAUDE.md `타입 / 영역 라벨` 절(아직 안 읽었으면 그 절을 읽는다)에 맞는지
  본다 — 타입 라벨이 표준 어휘(feat·fix·refactor·docs·chore) 중 정확히 하나인지,
  area가 그 절 기준대로인지(붙어야 하는데 없거나, 붙으면 안 되는데 있거나, 여러
  개이거나). 판단이 서지 않는 것도 어긋남으로 친다.
  **어긋나면 작업을 시작하지 말고, 고칠 라벨과 이유를 제안한 뒤 멈춘다.** 제안하는
  라벨은 레포에 있는 것(타입 5개·area 7개)만 쓴다. 승인 없이 이슈 라벨을 고치지 않는다
  — 팀원이 만든 이슈다. 답에 따라:
  - **고치라는 답** — `gh issue edit <번호> --add-label "<라벨>"`·`--remove-label
    "<라벨>"` 로 고친다(`gh issue edit` 에도 `--label` 은 없다 — 5단계 PR 갱신과 같은
    함정. 공백이 든 area 라벨은 따옴표로 감싼다). 사람이 GitHub에서 직접 고쳤다는
    답이어도 같다. 어느 쪽이든 위 `gh issue view` 로 **이슈를 다시 읽고** 이 확인부터
    다시 돈다.
  - **"그대로 진행"이라는 답** — **area 어긋남에만 받는다.** 타입 라벨이 없거나 둘 이상이면
    브랜치 이름의 `<타입>` 과 5단계 `--label <타입>` 을 정할 수 없으니, 그 경우는 고칠
    때까지 멈춘 채로 둔다. area 어긋남이면 이슈에 `라벨 유지 확인 (/issue): <지금 붙은 타입·
    area 라벨을 쉼표로>` 한 줄을 코멘트로 남기고(`gh issue comment <번호> --body "<그 줄>"`)
    진행한다. 그 라벨은 5단계가 PR에 그대로 옮기고, 무엇이 어긋났었는지는 6단계 최종 보고에
    적는다. **이 확인은 먼저 이 코멘트부터 본다** — 가장 최근 `라벨 유지 확인 (/issue):`
    코멘트의 목록이 지금 이슈의 타입·area 라벨과 같으면, 사람이 이 라벨을 이미 받아들인
    것이니 묻지 않고 넘어가되 그 어긋남은 이번 실행의 6단계 최종 보고에도 적는다. 재개한
    실행이든 새 실행이든 같다 — 재개인지는 2단계에서야 정해져 여기서는 가를 수 없다.
    상태·메타 라벨은 견주지 않는다(`question` 하나 붙었다고 같은 질문을 다시 하지 않게).
    다르면 그 뒤에 누가 타입·area를 바꾼 것이니 다시 본다.
- 재현 조건·기대 동작이 본문만으로 불분명하면 **작업 시작 전에** 질문하고 멈춘다.
  구현을 절반 해놓고 묻는 것보다 싸다.

## 2. 워크트리

이 단계는 **격리 상태에서도 그대로 돈다.** `git worktree add` 는 격리 세션의 명령 가드를 통과하고
(실측), `EnterWorktree(path:)` 는 이미 격리된 세션에서도 다른 워크트리로 바로 전환된다(도구 설명에
명시). 그러니 ExitWorktree로 복귀할 필요가 없다.

- **레포 루트**부터 구해 둔다:

  ```
  git worktree list --porcelain | sed -n '1s/^worktree //p'
  ```

  git이 본 워크트리를 **항상 첫 항목으로** 내므로 이 한 줄이 곧 레포 루트이고, 워크트리 안에서
  불러도 같다. `sed` 가 `worktree ` 접두어까지 떼므로 **출력 전체가 경로**다 — 그대로 복사해 쓴다.
  `grep '^worktree '` 로 받으면 접두어가 붙은 채라 명령에 넣으면 인자가 하나 더 붙어 깨진다.
  아래 `git worktree add` 가 이 절대경로를 쓴다 — 상대경로는 cwd 기준으로 풀려서, 격리 상태면 현재
  워크트리 **안에** 만든다. **받아 둔 뒤 한 번 확인한다** — `test -d "<레포 루트>" && echo ok`.
  실패하면 루트를 잘못 받은 것이니 멈추고 보고한다.
- `git fetch origin --prune` — 이 명령이 `fatal: bad object worktrees/<id>/HEAD … did not send all
  necessary objects` 로 죽으면(실측) 어떤 등록의 HEAD 가 **없는 커밋**을 가리키는 것이다. 레포 전체의
  fetch 가 막히므로 멈추고 그 `<id>` 를 짚어 보고한다 — 사람이 `.git/worktrees/<id>` 를 치워야 진행된다.
  잔재 확인과 워크트리 기준점 둘 다 원격 최신 상태를 전제로 한다.
  `--prune` 이 없으면 GitHub이 이미 지운 브랜치의 원격 추적 ref가 남아서 잔재로 오인된다 (머지 후
  재시도·재오픈 이슈를 막는다). (이 레포는 squash 머지 시 브랜치 자동 삭제가 **켜져 있다**(be 실측
  2026-10-27). 그래도 references 의 갈래들은 `origin/<브랜치>` 가 살아남은 경우를 다룬다 — 설정이 꺼지거나 사람이
  남겨 둘 수 있어서다.)
- **본 체크아웃에 서 있다면 로컬 `main` 을 최신으로 맞춰 둔다** —
  `git rev-parse --git-dir` 출력에 `/.git/worktrees/` 가 **없고**(없으면 본 체크아웃, 있으면 연결
  워크트리 — ASCII 부분만 보므로 정규화와 무관하다), `git symbolic-ref -q HEAD` 가 `refs/heads/main`
  이고, `git status` 가 깨끗하고, `git rev-parse main` 이 `git rev-parse origin/main` 과 다를 때만
  `git merge --ff-only origin/main` (방금 fetch했으므로 `pull` 로 또 받을 필요가 없다). 하나라도 안
  맞으면 상태만 보고하고 넘어간다. 앞의 두 조건이 다 필요하다 — `--git-dir` 만 보면 본 체크아웃이
  기능 브랜치에 있을 때 그 브랜치에 머지가 붙고, `symbolic-ref` 만 보면 그 상황에서 `main` 을 가져간
  연결 워크트리에서 참이 된다. **ff가 안 돼도**(로컬 main에 독자 커밋이 있는 경우) 멈추지 말고
  보고하고 넘어간다. 이건 본 체크아웃을 최신으로 유지하는 정돈일 뿐이다 — 리뷰 기준선은 4단계가
  `origin/main` 을 직접 지정하므로 로컬 main이 낡아도 영향이 없다. 7단계 (e)는 이 항목을 그대로
  가리킨다.
- **`/issue` 를 부른 문구에 앞선 세션의 꼬리가 딸려 왔으면 먼저 그 `remove` 의 사후 확인을 한다** — "앞선
  세션이 remove 까지 했고 사후 확인은 못 했다. 스냅숏 …, 대상 …" 꼴이다(`references/worktree.md` 제거 절차 3번
  "멈출 때"가 새 세션을 그렇게 부르라고 시킨다). 그 문서를 Read 해 "먼저 알아 둘 것"의 "앞선 세션의 꼬리"
  항목대로 `verify-removed.sh` 를 돌린다 — 아래 `residue.sh` 보다 먼저다. `residue.sh` 가 `CLEAN` 이면 이
  확인 없이 새 워크트리로 가 버리고, 잔재 조사·이어받기의 `find.sh` 는 스냅숏을 덮어써 확인이 불가능해진다.
- **잔재부터 확인한다** — 이슈 번호가 키다:

  ```
  bash "<스킬 디렉터리>/scripts/residue.sh" <이슈번호>
  ```

  이 이슈 번호의 브랜치(로컬·원격), `.claude/worktrees/` 아래 디렉터리, 등록된 워크트리 목록을 같은
  판별식으로 훑고, `.claude/worktrees/` 아래에서 등록이 없는 디렉터리(고아)를 가려낸다. 판별식과 등록
  판정 방법은 스크립트 머리말에 있다.
  - **`CLEAN`** — 이 이슈의 잔재가 없다. 아래 생성으로 간다. `other-orphan` 줄은 **다른 이슈의
    고아**다 — 막지 않고 최종 보고에 존재만 적는다. 그걸 이유로 멈추면 남의 잔재 하나가 이후 모든
    `/issue` 실행을 막는다.
  - **`RESIDUE`** — **여기서 멈추고 `references/worktree.md` 를 Read 해 "잔재 조사"부터 그대로
    따른다.** 이 워크플로가 스스로 하는 것은 **"이 이슈의 잔재 없음 → 새로 만든다"** 하나뿐이다 —
    이어받을지 버릴지는 사람이 정한다. 잔재는 드물고, 잘못 판단하면 되돌릴 수 없어서다.

- **워크트리는 `git worktree add` 로 만들고 `EnterWorktree(path:)` 로 들어간다** —
  두 단계다. 먼저 셸에서:

  ```
  git worktree add --no-track "<레포 루트>/.claude/worktrees/<타입>+<이슈번호>-<기능>" -b "<타입>/<이슈번호>-<기능>" origin/main
  ```

  그다음 **EnterWorktree 도구**를 `path: "<위 경로>"` 로 호출한다 (셸 명령이 아니다).
  디렉터리 이름은 브랜치명의 슬래시를 `+` 로 바꾼 평탄한 한 단계로, 기존 워크트리들과
  같은 모양이다.

  **`git worktree add` 가 실패하면 멈추고 출력을 그대로 보여준다**(`already exists`,
  `missing but already registered`, `is already used by worktree at` 등) — 잔재 확인이 못 잡은
  디렉터리나 등록이 남아 있다는 뜻이다. `-f` 로 덮어쓰지 않는다 — 그 자리의 작업물이나 다른 세션의
  등록을 밀어낸다.

  **세 메시지 중 무엇으로 실패하든 `-b` 가 만든 브랜치는 남는다**(실측 — git 이 브랜치를 먼저 만들고
  워크트리 등록에서 죽는다). `origin/main` 자리의 빈 브랜치이고 옛 작업이 아니니 보고에 그렇게 적는다
  (다음 세션의 `residue.sh` 가 `branch` 줄로 잡고, 잔재 정리가 치운다). 디렉터리만 치우고 **같은 명령을
  다시 치면** 이번엔 `fatal: a branch named '<브랜치>' already exists`(rc 255)로 죽는다 — 잔재가 아니라
  방금 우리가 남긴 브랜치다. 그때는 `git rev-parse "refs/heads/<브랜치>"` 와 `git rev-parse origin/main` 이 같은지
  보고(`refs/heads/` 를 붙이는 이유는 `references/worktree.md` "먼저 알아 둘 것" — 같은 이름의 태그가 있으면
  맨 이름은 태그로 풀린다),
  **같으면 `-b` 와 `--no-track` 을 둘 다 빼고** `git worktree add "<경로>" "<브랜치>"` 로 그 브랜치에 붙인다
  (`-b` 만 빼면 `--[no-]track can only be used if a new branch is created` 로 또 죽는다 — 실측). 다르면 그
  브랜치에 커밋이 있는 것이니 멈추고 보고한다. **`is already used by worktree at` 으로 죽었으면 이 재시도를
  하지 않는다** — 그 이름을 쥔 등록이 있다는 뜻이라 `-b` 를 빼고 쳐도 같은 메시지로 죽는다(실측). 그때는
  `references/worktree.md` 를 읽고 잔재 조사로 간다. 그리고 그 실패 뒤에는 그 등록의 HEAD 가 새 빈 브랜치로
  풀려 **`dangling` 표시가 사라지고 살아 있는 등록처럼 보인다**(실측). 그 안의 `git status` 는 옛 체크아웃
  전체를 변경으로 내므로, 보고에 그 사실까지 적어야 다음 세션이 "남이 쓰는 중"으로 오진하지 않는다.

  **`git worktree add` 에는 `--` 를 넣지 않는다.** `add` 자체가 `--` 를 못 받는 건 아니다
  (`add -- "<경로>" HEAD` 는 잘 돈다 — 실측). 막히는 건 **이 명령 모양** 때문이다: `-b "<브랜치>"
  origin/main` 이 경로 **뒤에** 오는데, `--` 를 앞에 끼우면 그 둘까지 위치 인자로 읽혀 `add` 가 받는
  두 자리를 넘겨 usage 에러로 죽는다(실측). (`remove`·`lock`·`unlock` 에는 반대로 넣는다 —
  `references/worktree.md`.)

  **`--no-track` 을 뺀 채 `origin/main` 에서 따면 새 브랜치의 upstream이 `origin/main`
  으로 걸린다**(git 기본값, 실측). 그러면 5단계 전에 어떤 이유로든 멈췄을 때 사람이
  그 워크트리에서 맨 `git push` 를 치면 "upstream이 브랜치 이름과 다르다"로 거부되고,
  맨 `git pull` 은 `origin/main` 을 작업 브랜치에 **머지해 버린다** — 그 머지 커밋이
  PR에 들어간다. `--no-track` 이면 5단계의 `push -u` 전까지 upstream이 없어 둘 다
  그냥 안내 메시지로 끝난다. (이어받은 옛 브랜치는 이 보장이 없어서
  `references/worktree.md` 이어받기 5번이 따로 뗀다.)

  이 명령은 **격리 세션 안에서도 통과하고, 한글이 든 절대경로도 정상 동작한다**
  (둘 다 limbing-ios 에서 실측). 그래서 이전 `/issue` 실행의 워크트리에 격리된 채로
  들어와도 복귀 없이 그냥 만들면 된다 — 경로가 레포 루트 기준 절대경로라 중첩될
  일이 없다.

  **`EnterWorktree(name:)` 을 쓰지 않는다.** 두 가지 이유다:
  - 준 이름을 그대로 쓰지 않는다 — 슬래시를 `+` 로 바꾸고 앞에 `worktree-` 접두어까지
    붙여서 `fix/283-x` 가 `worktree-fix+283-x` 가 된다. 위 잔재 탐지와 7단계 후처리가
    전부 이름으로 대상을 특정하므로 이름이 흔들리면 그 브랜치는 다음 세션에서 유령이
    된다. `branch -m` 으로 되돌릴 수는 있지만 그 단계가 돌기 전에 세션이 죽으면 그대로
    남는다.
  - **워크트리를 세션 pid로 잠근다.** 잠금 자체는 좋은 보호지만, 그러면 이 워크플로가
    잠금을 만나 "내 것인지, 그 세션이 살아 있는지"를 가려야 하고, 그 판별(조상 pid
    비교, 시작 시각 문자열 대조)이 실제로 여러 번 사고를 냈다 — 로케일, 후행 공백,
    형제 프로세스, 격리 세션의 명령 가드. `git worktree add` 로 만들면 우리 워크트리는
    **잠기지 않으므로**, 잠금이 보이면 남의 것이고 규칙은 "건드리지 않고 보고한다"
    한 줄로 끝난다.

  그 대가로 우리 워크트리는 다른 세션의 진입·삭제를 잠금으로 막지 못한다. 그 역할은
  잔재를 만나면 묻는다는 규칙과 이어받기 3번의 `git status` 가 한다 — 열린 PR, 미푸시 커밋, 미커밋
  변경, 등록된 채 아직 커밋 전인 워크트리는 자동으로 지우지도 이어받지도 않는다.

- **진입 직후 확인해 기록한다** — 이후의 리뷰·PR·삭제가 전부 이 기록을 쓴다.
  **첫 항목이 실패하면 나머지를 돌리지 않는다**:
  - `git branch --show-current` 가 **방금 만든 브랜치와 같은지** 본다(이어받기는 그 절차 2번에서 이미
    했다). 다르면 EnterWorktree(path:) 호출이 실패했거나 건너뛰어진
    것이다 — 세션은 본 체크아웃(`main`)이나 직전 이슈의 워크트리에 그대로 있다.
    **멈추고 보고한다.** (경로로 확인하지 않는다 — 위 "경로를 문자열로 비교하지 않는다". 브랜치
    이름이 곧 워크트리 신원이다.)
  - `git rev-parse HEAD` == `git rev-parse origin/main` — **새로 만든 워크트리에만**
    적용한다 (이어받은 워크트리는 커밋이 쌓여 있어 당연히 다르니 이 검사를
    건너뛴다). 생성 직후인데 두 값이 다르면 기준점이 origin/main이 아닌 것이니
    멈추고 보고한다. (`merge-base --is-ancestor`는 HEAD가 앞서 있어도 통과하므로
    이 검사로는 못 잡는다.)

## 3. 구현

- 검증 게이트는 **CLAUDE.md 빌드 절의 기본 게이트**를 그 절이 정한 파일을 고쳤을 때 실행한다 (그 밖의
  파일은 자동 게이트 없이 리뷰로 본다) — 게이트의 대상·명령·한계·확정 검증의 소재 모두 그쪽이 정본이다
  (여기 명령을 박아두면 게이트가 바뀔 때 낡은 사본이 된다). 시그니처나 이름을 바꿨으면 선언부·호출부를
  grep으로 함께 확인한다.
- **게이트의 `./gradlew` 는 Bash 제한 시간을 넉넉히(10분) 주거나 `run_in_background` 로 돌린다** — 새 워크트리의
  첫 빌드는 의존성 다운로드로 수십 초~수 분 걸릴 수 있다(limbing-aos 에서는 2분을 넘겼다 — aos 실측 2분 14초~2분 44초).
  기본 제한 시간에 끊기면 데몬이 그 빌드를 취소하므로(aos 실측, `references/worktree.md` 2번) 게이트를 처음부터 다시
  돌려야 한다.
- 구현이 끝나면 **기능 단위로 커밋한 뒤** 리뷰 루프에 들어간다 — 리뷰한 코드와
  커밋된 코드가 같아야 라운드 기록이 재현 가능하고, PR에 담기는 것도 정확히
  리뷰를 통과한 그 코드가 된다. **커밋할 때마다** `git status`로 의도하지 않은
  파일이 섞이지 않았는지 본다 (특히 비밀 값 파일 `.env`·`application-local.*` —
  `.gitignore` 에 있지만 강제 add(`-f`)는 막지 못한다. PR 시점 점검으로는 이미 커밋에 들어간 파일이 안 보인다).

## 4. 셀프 코드리뷰 루프

- 첫 라운드 전에 `git diff --stat origin/main...HEAD` 가 이 브랜치의 변경 파일과
  일치하는지 본다 — baseRef 오설정 같은 기준선 붕괴를 리뷰 한 판 태우기 전에
  공짜로 잡는다. 다르면 멈추고 보고한다.
- **매 라운드 `/code-review high origin/main...HEAD` 로 돌린다** — 레벨과 범위를 둘 다
  명시한다.
  - **레벨**을 안 주면 직전에 쓴 레벨을 재사용해서 게이트 깊이가 실행마다 달라진다.
  - **범위**를 안 주면 `/code-review` 는 `git diff @{upstream}...HEAD` 를 쓰고, upstream이
    없으면 `main...HEAD` 나 `HEAD~1` 로 물러선다(설치된 버전의 Phase 0 프롬프트에
    그렇게 적혀 있다 — 실측). 격리 세션에서는 인용 없는 `@{upstream}` 이 명령 가드에
    막히므로 **어느 갈래로 풀리는지 알 수 없다** — 낡은 로컬 `main` 이면 남의 커밋까지
    이 브랜치 변경으로 리뷰되고, `HEAD~1` 이면 마지막 커밋만 리뷰되고 앞 커밋은 게이트를
    그냥 통과한다. 범위를 주면 리뷰가 그것을 스코프로 삼는다 — 실제로 그 형태로
    여러 라운드를 돌려 스코프가 맞는 것을 확인했다.
    **다만 이건 결정론적 보장이 아니다**(실측): 인자는 `Review target: \`…\`` 로
    프롬프트에 **그대로 실리는 자유 텍스트**이고, Phase 0 지시가 열거하는 형태는
    "PR 번호 / 브랜치명 / 파일 경로"뿐이라 범위는 그 목록에 없다. 즉 지키는 건
    리뷰 모델의 판단이다. 그래서 **리뷰 결과가 온 파일 목록을
    `git diff --stat origin/main...HEAD` 목록과 대조한다** — 이 목록은 **매 라운드
    다시 받는다.** 첫 라운드 것을 재사용하면 안 된다: P1·P2를 고치다 보면 파일이
    늘어나고(CLAUDE.md 의 아키텍처 절을 따라 고치다 보면 Service·Repository·DTO 를 새로 만들게 된다),
    그러면 다음 라운드가 그 새 파일에 단 정당한 지적을 "기준선 밖"으로 버리고 다시
    돌리기를 반복하다 상한에서 끝난다. 이 브랜치가 안 건드린
    파일에 지적이 달렸으면 **버리기 전에 그 지적을 읽어 본다.** 두 가지가 섞여 있다:
    **이 브랜치가 깨뜨린 호출부**(시그니처를 바꿨는데 안 고친 곳)면 파일이 diff에 없어도
    **정당한 지적이고 고쳐야 한다** — 이건 리뷰 범위 안이다. 그게 아니라 이 작업과
    아무 상관 없는 파일들이 무더기로 나오면 기준선이 어긋난 것이니 그 라운드를
    버리고 다시 돌린다. 무조건 버리면 진짜 P1이 라운드마다 다시 올라오고 매번
    버려지다 상한에서 끝난다.
    (`Review target` 에코는 인자를 그대로 되돌려줄 뿐이라 무엇을 diff했는지는 알려주지
    않는다 — 파일 목록으로 봐야 한다.)
    **대조는 있을 때만 하고, 없다고 버리지 않는다.** 리뷰 보고에 스코프(본 파일
    목록·개수)가 적혀 있으면 변경 파일과 맞춰 보고 어긋나면 다시 돌린다. **적혀
    있지 않으면 그 라운드도 정상으로 친다** — 리뷰가 스코프를 밝힐지는 보고 형식에 달렸고 우리가
    강제할 수 없다. 특히 **지적 0건인 라운드는 대개 아무것도 안 적는다**(찾은 게
    없으니 쓸 것도 없다). 그걸 "스코프를 안 밝혔으니 무효"로 치면 게이트를 닫을
    라운드마다 버려져 루프가 상한까지 돌고 PR을 영영 못 만든다.
    즉 **빈 diff를 본 라운드를 확실히 가려낼 방법은 없다.** 방어는 매 라운드 범위를
    주는 것이고, 이 대조는 어긋남이 눈에 보일 때 잡는 보조 수단이다.
    **부분 스코프(`HEAD~1`)는 이 대조로 못 잡는다** — 지적이 변경 파일의 부분집합이라
    양쪽 검사를 다 통과한다. 지적이 없는 파일이 곧 안 본 파일도 아니라서 목록만으로는
    구분이 안 된다. 완전한 탐지는 없고, 방어는 **매 라운드 범위를 주는 것**이다.
    다만 커밋이 여럿인데 지적이 **마지막 커밋이 건드린 파일에만** 몰려 있으면 의심하고
    한 번 더 돌린다 — 확정은 아니고 신호다.
    upstream을 설정하거나 되돌리는 절차는 없다. 새 브랜치는 `--no-track` 이라 push
    전까지 upstream이 없고, 이어받은 브랜치는 `references/worktree.md` 이어받기 5번이 upstream을
    떼 둔다.
- 결과를 codex와 같은 어휘로 분류한다:
  - **P1** — 크래시·데이터 손실·명백한 오동작
  - **P2** — 실사용에서 문제가 되는 결함, 계약 위반, 놓친 엣지 케이스
  - **P3** — 사소한 개선·스타일
- P1·P2 를 반영하고 다시 리뷰한다. **P1·P2 가 0건이 될 때까지 반복.** 코드만으로 가릴 수 없는 후보는 아래
  안전장치의 "가릴 수 없음" 규칙을 따르고, 거기서 체크리스트로 넘긴 후보는 이 셈에 들지 않는다.
  P3 는 판단해서 반영하되 루프 조건에 넣지 않는다.
- 반영 후에는 (게이트 대상 파일을 고쳤으면) 기본 게이트를 다시 돌려 확인하고 커밋하고 나서 다음 리뷰를
  돌린다 — 컴파일 오류 하나로 값비싼 리뷰 한 판을 태우지 않기 위해.
- **매 라운드를 기록한다** — 이것을 **라운드 기록**이라 부르고, 5단계가 PR 본문에, 6단계가 최종 보고에 그대로
  싣는다. 4단계에 들어간 뒤로는 **어느 단계에서 어떤 이유로 멈추든 그 보고에도 싣는다**(앞 실행에서 이어 온 것도) —
  사람이 멈춘 자리에서 판단하려면 그때까지의 판정이 보여야 한다. PR 본문에 아직 안 실린 라운드가 있으면(PR 이 없을
  때도) 그 라운드를 "PR 에 안 실린 라운드"로 따로 밝히고, 이어서 시킬 때 레포 이름을 붙여 부르며(`/issue <번호> be`)
  이 보고를 함께 붙여 달라고 적는다 — 그 라운드는 이 보고에만 남는다.
  항목은 ① 전체 지적과 부여한 등급·반영 여부(미반영분은 P3 판단 포함) ② 센 라운드인지(n/10)와
  안 셌으면 그 사유, 멈춘 리뷰를 깨워 받은 결과인지 ③ 판정을 리뷰가 냈는지 세션이 냈는지(사람이 냈으면
  사람) ④ P1·P2 가 아니라고 본 후보와
  "가릴 수 없음"으로 본 후보의 근거 ⑤ "가릴 수 없음" 후보를 어디로 넘겼는지(멈춤·체크리스트)다.
  등급과 판정을 매기는 것도 코드를 쓴 자신이므로, 다운그레이드가 사람 눈에 보여야 게이트가 신뢰된다 — 센
  라운드 분류도 자신이 하고, 그것이 루프가 언제 끝나는지를 정한다.
- **라운드 기록은 브랜치 하나에 한 줄로 잇는다** — 2단계에서 이어받은 실행도, 6단계의 재리뷰도 앞 기록에 이어 적고
  이어 센다.
  - **첫 라운드 전에 앞 기록을 정한다.** 앞 기록은 이 브랜치 PR 본문의 라운드 기록 칸(5단계)과, 사람이 이번 요청에
    붙여 준 앞 실행의 멈춤 보고다. PR 은 `gh pr list --head "<브랜치>" --state open --limit 100 --json number,baseRefName`
    으로 찾는다 — 이 조회가 0 이 아닌 종료 코드로 끝나면 "PR 없음"으로 치지 않고 멈추고 보고하고, `main` 이 아닌 base 의
    PR 이 있거나 `main` base 의 PR 이 둘 이상이면 5단계 그 항목들처럼 묻는다. 둘 다 있으면 센 라운드가 많은 쪽을 쓴다 — 보고는 PR 에 안 실린 라운드까지 담을 수 있고,
    거꾸로 오래된 보고가 붙을 수도 있다. 사람이 몇 라운드째부터 셀지 알려 주었으면 그것을 따른다. 아무것도 없으면
    1/10부터 세되, 이어받은 실행이면 까닭이 무엇이든 앞 기록을 찾지 못했다고 라운드 기록과 보고에 적는다.
  - 앞 기록의 센 라운드 수가 n/10 이고, 끝에 이어진 세지 않는 실행·깨워 받은 결과의 수가 아래 연속 3회 셈이다.
    이번 실행의 라운드는 그 뒤 번호로 이어 적는다.
  - 이어 센 수가 이미 10 이상이면(다음 라운드가 상한을 넘긴다 — 상한으로 멈췄거나, 상한까지 돈 브랜치를 6단계에서
    다시 리뷰한다) 사람이 몇 번 더 돌릴지 밝혔을 때만 그만큼 상한을 늘려 돌고, 밝히지 않았으면 첫 라운드 전에 묻는다.
    연속 3회로 멈춘 뒤 사람이 다시 돌리라고 했으면(이어받으라는 답도, 같은 대화의 지시도) 연속 셈을 0부터 센다. 어느
    쪽이든 라운드 기록에 적는다(be #26 은 상한을 넘겨 1회 더 돌렸다).
- 안전장치:
  - 리뷰가 최종 보고 없이 멈추면(중간 상태로 정지, 검증자 대기 등) 먼저 **깨워서**
    있는 결과로 종결시키고, 그래도 안 나오면 **다시 돌린다**. 사람에게 넘기는 건
    그다음이다.
  - **센 라운드**는 리뷰가 최종 지적 목록을 낸 실행이다. 기준선이 어긋나 후보를 판정하지 않고 버린 라운드도
    센다 — 위의 "상한에서 끝난다"는 문장들이 그 라운드를 두고 한 말이다. 멈춘 리뷰를 깨워 받은 결과도 세지만,
    리뷰가 끝까지 돌지 못했을 수 있어 그 결과로는 게이트를 닫지 않는다 — 거기 나온 P1·P2 는 반영하고, 게이트는
    다음 실행으로 판정한다. 최종 목록 없이 끝난 실행(깨워도 안 나왔거나 사용량 한도로 죽었다)은 세지 않는다.
  - 게이트 판정(P1·P2=0)에는 **완결 라운드**만 쓴다. 완결 라운드는 깨워서 받지 않은 센 라운드 가운데 후보마다
    판정이 붙은 라운드다. 판정은 "결함(P1·P2·P3)"·"결함 아님"·"가릴 수 없음" 가운데 하나다 — 지적 0건으로 끝난
    최종 보고도 완결이다. 리뷰가 판정 없이 목록만 냈으면(be #26) **세션이 후보마다 코드를 확인해
    판정과 등급을 라운드 기록에 적으면 완결로 친다.** 판정하는 쪽이 코드를 쓴 자신일 수 있으니, 사람이 그 판정을
    따라가 볼 수 있게 남긴다(5단계가 이 기록을 PR 본문에 싣는다):
    - P1·P2 가 아니라고 본 후보("결함 아님"이든 P3 든)에는 근거를 적는다 — 근거가 된 코드 위치(파일:줄과 그 라운드의
      커밋 sha)와 그 지적이 왜 성립하지 않거나 사소한지. 리뷰가 붙인 판정이어도 근거가 없으면 세션이 이 기준으로
      다시 본다.
    - 코드만 읽어서는 가릴 수 없는 후보(실행 순서·타이밍·환경에 달린 것)는 판정을 지어내지 않고 "가릴 수 없음"으로
      적는다. 이것에도 근거를 적는다 — 실행 때 무엇에 따라 갈리는지와, 실제라도 P1 감이 아니라고 본 이유. 근거 없이
      이 판정을 쓰면 불편한 P2 를 게이트 밖으로 빼는 길이 된다. **실제라면 P1 감**(위 분류의 P1 — 크래시·데이터 손실·
      명백한 오동작)이면 루프를 멈추고 그 후보와 라운드 기록을 보고한다 — 사람이 재현하거나 판단한다. 사람이 판정을
      주면 그것을 그 후보의 판정으로 라운드 기록에 적고 4단계를 이어 간다(그 라운드가 완결 라운드 조건을 채우면 게이트
      판정에 쓴다).
      그 밖이면 게이트는 막지 않고 5단계의 확인 체크리스트(개발자가 눈으로 확인해야 할 것)에 올려 사람에게
      넘긴다 — 리뷰가 확인 없이 후보를 넉넉히 내놓아 이런 추측성 후보가 라운드마다 섞이므로, 다 막으면 게이트가
      닫히지 않거나 쓸데없는 방어 코드가 붙는다.
  - **10회**(회 = 센 라운드 수)를 넘기거나 같은 지적이
    반영↔재출현을 반복하면 루프를 멈추고 상황을 보고한다. 열 번을 넘긴 라운드는 대개 자기
    수정의 회귀를 쫓는 데 쓰인다(ios #376). 이 사본은 한때 "그 시간에 PR을 올려 codex에 넘기는 편이
    낫다"며 5회로 줄였지만, 이 레포 PR에 codex가 붙지 않은 동안은 셀프리뷰가 유일한 자동 리뷰라서
    10회로 되돌렸다(be #21) — codex를 붙이면 이 상한을 다시 정한다.
    **세지 않는 실행이나 깨워 받은 결과가 섞여 연속 3회**여도 멈추고 보고한다 — 이 둘만 세고, 깨우지 않고 최종
    목록을 낸 실행은(P1·P2 가 나왔어도) 연속을 끊는다. 깨워 받은 결과는 세지만 게이트를 닫지 못해, 리뷰가 매번
    멈추면 상한까지 헛돈다. 안 세는 실행은 상한에 닿지 않으므로, 이 갈래가 없으면 최종 목록을 못 내는 리뷰가
    루프를 끝없이 돌린다(스톨도 여기 든다 — 위 깨우기→재실행 항목은 순서만 정하고 횟수를 막지
    않는다). 멈춘 자리에서 정리할 git 상태는 없다 — 새 브랜치는 `--no-track` 이고 이어받은
    브랜치는 이어받기 절차에서 upstream을 떼 두었으며, 리뷰 범위는 직접 주므로 임시 upstream
    같은 건 없다.

## 5. PR

- 커밋은 기능 단위로 쌓은 그대로 둔다 — 히스토리를 다시 쓰지 않는다 (squash 병합 전제).
- 스테이징·커밋 메시지·PR 제목·`Closes`·라벨·AI 표기 금지는 CLAUDE.md
  규칙을 따른다 (`Git / 협업 규칙`·`타입 / 영역 라벨` 절에 나뉘어 있다).
- **push 전에 PR 라벨에 쓸 값을 정한다 — 이슈를 다시 읽는다**: `gh issue view <번호>
  --json labels,milestone`. 1단계에서 읽은 값을 그대로 쓰면, 리뷰 루프가 도는 사이 사람이
  이슈 라벨을 바꿨을 때 PR이 그 결정을 되돌린다. 다시 읽은 값이 1단계 때와 다르면 사람이
  바꾼 것이니 **그 값을 쓰고** 달라진 사실을 최종 보고에 적는다 — area 가 기준과 어긋나
  보여도 사람이 방금 정한 것이니 다시 묻지 않는다. 타입이 다른 하나로 바뀌었으면 PR 제목의
  타입 접두어도 새 타입으로 쓰고(squash 커밋 메시지가 된다), 브랜치 이름은 바꾸지 않은
  채(이어받기 6번과 같은 이유) 그 사실도 최종 보고에 적는다. **다만 타입 라벨이 없거나 둘 이상이
  됐으면 멈추고** 고칠 타입 라벨을 제안한다 — 아래 PR 생성의 `--label <타입>` 이 비거나
  기존 PR 갱신이 PR의 타입 라벨까지 뗀다. push 앞이라 멈춰도 원격에는 아무것도 안 남는다.
  고치라는 답이면 1단계의 "고치라는 답" 갈래처럼 세션이 `gh issue edit` 로 고친다. 고쳤거나
  고쳤다는 답을 받으면 이슈를 다시 읽어 **타입만** 다시 보고 이 자리에서 이어 간다 —
  1·2단계로 되돌아가지 않는다(1단계를 다시 돌면 사람이 방금 정한 area 를 또 묻고, 2단계를
  다시 돌면 `residue.sh` 가 이 브랜치를 잔재로 잡는다). 고친 타입이 1단계 때와 다르면 위
  타입 변경과 같이 다룬다. 구현한 변경(`git diff --stat origin/main...HEAD`)에 비춰 area 판단이 1단계와 달라
  보여도(여러 모듈에 걸치게 됐거나 모듈 밖 작업이었거나) 멈추지 않고 최종 보고에 적는다 —
  이슈 라벨을 고칠지는 사람이 정한다.
- **push 전에 이 브랜치를 뒷받침하는 열린 PR의 base를 본다** —
  `gh pr list --head "<브랜치>" --state open --limit 100 --json number,baseRefName`.
  **`main` 이 아닌 base의 PR이 하나라도 있으면 push하지 않고 그 번호·base를 보여주고
  묻는다.** push는 그 PR에 이번 커밋을 **전부 얹어 버리고**, 아래 기존 PR 조회는
  `--base main` 이라 그 PR을 못 보고 지나가 `main` 대상 PR을 새로 만든다. 결과가
  "`main` 이 아닌 base 의 PR에 엉뚱한 작업이 들어갔고, 같은 브랜치로 PR이 둘"이 된다(이 레포는 `main`
  하나로 운영하지만 사람이 다른 base 로 열 수 있다).
  **아래 `--base main` 필터는 이걸 못 막는다** — 그건 메타데이터 편집만 막고,
  이미 나간 push는 되돌릴 수단이 `--force` 뿐인데 이 워크플로는 그걸 금지한다.
  이 상황은 이어받기로 온 실행에서만 생긴다(새로 만든 브랜치에는 PR이 없다).
- 그다음 `git push -u origin HEAD` 로 **먼저 푸시한다.** 아래 어느 갈래로 가든 push가 앞이다 —
  갱신 갈래에서 이걸 건너뛰면 PR 제목·본문만 바뀌고 코드는 로컬에 남은 채 "완료"로
  보고하게 된다.
  **non-fast-forward로 거부되면** 리뷰 루프가 도는 사이 원격이 앞선 것이다(사람이
  GitHub에서 제안을 적용했거나 다른 머신이 push했다). `git fetch origin "refs/heads/<브랜치>"` 로
  받아 보고 **`git merge --ff-only "origin/<브랜치>"` 가 되면 그대로 잇고 다시
  push한다.** (`refs/heads/` 를 붙이지 않으면 같은 이름의 태그가 있을 때 태그만 받고
  `origin/<브랜치>` 가 안 생긴다 — `references/worktree.md` "먼저 알아 둘 것".)
  ff가 안 되면(양쪽에 다른 커밋) **묻는다** — `--force` 는 쓰지 않는다.
  남의 커밋을 날리고, 그게 PR에 이미 반영된 리뷰 수정이면 그대로 사라진다.
  이어받기 4번의 따라잡기는 실행 **시작 시점**에만 도므로 이 자리를 못 막는다.
  **ff로 붙인 커밋은 리뷰를 안 거친 코드다.** 4단계 게이트는 그 전에 닫혔고,
  3단계는 "PR에 담기는 것이 정확히 리뷰를 통과한 그 코드"라고 약속한다. 그러니
  붙인 뒤 **4단계를 한 라운드 더 돌리거나**, 예산이 없으면(상한에 닿았을 때도) **최종 보고에 "이
  커밋들은 셀프 리뷰를 안 거쳤다"고 명시한다.** 조용히 넘어가면 게이트를 통과했다는
  보고와 실제 PR 내용이 어긋난다.
- 그다음 **이 브랜치의 PR이 이미 있는지 본다** — `gh pr list --head "<브랜치>"
  --base main --state open --limit 100 --json number`. 중단됐다 재개한 실행은 PR이 이미 있을 수 있고, 그
  상태로 `gh pr create` 를 부르면 실패한다. `--json number` 없이 부르면 사람이 읽는
  표가 나와서 번호를 긁어내야 한다 — 아래 갱신 명령이 번호를 받으므로 바로 쓸 수
  있는 형태로 받는다. 없으면 아래 본문 파일을 새로 써서 "PR 생성"으로, 있으면 본문 파일을 그 PR 의 본문에서
  시작해 "이미 있는 PR 갱신"으로 간다 — 그래서 이 확인이 본문 파일보다 앞이다.
  **`--base main` 을 빼지 않는다** — `--head` 는 head 브랜치만 거르므로, 이 브랜치가
  `main` 이 아닌 base로 열어 둔 PR이 있으면 그걸 "이미 있는 PR"로 잡아 제목·본문·
  라벨·마일스톤을 덮어쓰고, 정작 만들려던 `main` 대상 PR은 안 만든다.
  **그래도 둘 이상 나오면 고르지 말고 보여주고 묻는다** — 갱신 명령에 넣을 `<번호>`
  가 정해지지 않는다(`references/worktree.md` 잔재 조사의 PR 조회와 같은 원칙).
- **본문 파일은 `<워크트리 루트>/scratchpad/pr-body.md`(아래 명령의 `<파일>`)로 만들고, 다 쓰면
  지운다.** 이름을 고정해 두는 것은 앞 실행이 남긴 파일을 찾아 덮어쓰고 지우기 위해서다.
  `<워크트리 루트>` 는 `git rev-parse --show-toplevel` 로 받는다 — 지금 서 있는 워크트리를 그대로 낸다(2단계에서 받아 둔 `<레포 루트>` 는 **본 체크아웃**이라
  여기 쓰면 파일이 엉뚱한 트리에 생긴다). 이 명령은 격리 세션에서도 통과한다(실측).
  생성 갈래는 Write 도구로 새로 쓴다(앞 실행이 남긴 파일이 있으면 Read 한 뒤 덮어쓴다 — Write 는 읽지 않은 파일을
  덮어쓰지 않는다). **갱신 갈래는 기존 본문에서 시작한다** — 새로 쓰면 앞 실행이 실은 라운드
  기록과 체크리스트(사람이 체크한 칸까지)가 PR 에서 지워진다. 아래 두 줄을 한 줄씩 따로 쳐서 받고, 그 파일을 Read
  한 뒤 Edit 로 고친다(무엇을 더하는지는 아래 라운드 기록 항목. 받은 본문이 비어 Edit 할 자리가 없으면 Write 로 쓴다):

  ```
  mkdir -p "<워크트리 루트>/scratchpad"
  gh pr view <번호> --json body --jq '.body | gsub("\r"; "")' > "<파일>"
  ```

  `gh pr view` 가 0 이 아닌 종료 코드로 끝나면 그 파일을 지우고 멈추고 보고한다 — 리다이렉트는 그래도 빈 파일을
  만들고, 그 파일로 갱신하면 기존 본문이 지워진다. `gsub` 는 웹 편집기가 남길 수 있는 CR 을 떼어 Edit 가 줄 끝에서
  어긋나지 않게 한다.
  셸 히어독(`mkdir -p … && cat > … <<'EOF'`)은 격리 세션의 명령 가드가 "too complex"로 거부하므로 본문을 셸로
  쓰지 않는다 — 위 두 줄은 따로 치면 통과한다(be 실측). 위치가 중요한 이유는 **이 파일이 마지막
  커밋 뒤에 생기기 때문**이다 — 추적되지 않는 파일로 남으면 나중에 7단계의
  `git worktree remove` 가 `contains modified or untracked files` 로 거부되고,
  그 자리의 안내는 이걸 "커밋 전에 중단된 실작업"으로 진단해 사람에게 넘긴다.
  성공한 실행마다 그 오진이 난다.
  **`scratchpad/` 라는 위치와 삭제가 둘 다 필요하다** — `.gitignore` 에 있어서 남아 있어도
  `worktree remove` 자체는 막지 않지만, 이 레포에서는 그 앞의 `ignored-check.sh` 가
  `scratchpad/` 안을 들여다보고 남은 본문 파일을 `KEEP` 으로 잡아 7단계 정리를 한 번 멈춘다
  (무엇이 든 파일인지 스크립트가 가리지 않으므로 사람이 지워야 한다). 그러니 PR 명령이 끝나면
  반드시 지운다. 아래 실패 갈래(라벨 없음·따옴표 누락·본문 길이)로 멈췄을 때 남은 파일도 다음에 이어서
  PR 을 만든 뒤 지운다. 파일을 다른 곳으로 옮기지 말 것 — 위치를 바꾸는 순간 위 오진이 되살아난다.
  **경로는 절대경로로 쓴다**(Write 도구도 절대경로를 요구한다). 상대경로로 적으면
  본 체크아웃 쪽에 만들어질 수 있고, 그러면 워크트리에서 도는 `--body-file` 이 없는
  파일을 가리켜 PR 단계가 그대로 실패한다.
- **PR 생성** — `gh pr create --title "<제목>" --label <타입> --body-file <파일>`
  로 **PR을 실제로 만든다** — 라벨·마일스톤은 플래그로 **명시해야** 붙고(없으면
  제목·본문만 있는 PR이 생긴다), **공백이 든 값(제목·area 라벨·마일스톤)은 반드시
  따옴표로 감싼다** — 안 그러면 셸이 인자를 쪼개서 명령이 거부된다.
  - **라벨은 방금 다시 읽은 이슈 라벨을 그대로 옮긴다** — `<타입>` 은 이슈의 타입
    라벨이고, area는 붙은 것마다 `--label "area: <영역>"` 로 붙인다. 이슈에 area가
    없으면 플래그째 생략한다 — 늘 넣으면 **없는 라벨을 넘겨 명령 전체가 실패**한다.
  - 마일스톤은 해당되면 `--milestone "<이름>"` 추가.
  - 본문을 인라인으로 넘기지 않는 이유: 백틱이 셸에서 실행되는 사고가 있다.
- **이미 있는 PR 갱신** — `gh pr edit <번호> --title "<제목>" --body-file <파일>`.
  `gh pr edit` 에는 **`--label` 이 없다** — `--add-label` / `--remove-label` 이다
  (`create` 의 플래그를 그대로 옮기면 `unknown flag` 로 명령 전체가 실패한다).
  **제목도 함께 갱신한다** — squash 병합이라 PR 제목이 곧 `main` 의 커밋 메시지인데,
  재개 중 범위가 바뀌었으면 낡은 제목이 그대로 박힌다.
  **라벨·마일스톤도 맞춘다.** 사람이 먼저 연 PR이거나 라벨 단계에서 죽은 이전 실행이
  남긴 PR이면 CLAUDE.md `타입 / 영역 라벨` 절의 규칙을 어긴 채로 남아 있을 수
  있는데, 갱신 경로가 제목·본문만 건드리면 그대로 통과해 버린다.
  `gh pr view <번호> --json labels,milestone` 으로 현재 상태를 읽고:
  - **타입·`area:` 라벨은 방금 다시 읽은 이슈 라벨과 똑같이 맞춘다** — 이슈의 타입·
    area를 `--add-label` 로 채우고, 이슈에 없는 타입 라벨(feat·fix·refactor·docs·chore
    중)과 `area:` 라벨은 `--remove-label` 로 뺀다. 채우기만 하면 라벨이 둘이 되어 규칙을
    오히려 어긴다. PR에만 있는 라벨은 사람이 직접 달았을 수 있지만, 1단계에서 이슈 라벨을
    사람과 확인했으니 이슈가 기준이다. **뺀 라벨은 6단계 최종 보고에 적는다** — PR
    타임라인에도 누가 뗐는지 남으므로 실행이 도중에 끊겨도 흔적은 있다.
  - **상태·메타 라벨**(`question`, `help wanted` 등)은 CLAUDE.md가 허용하는 것이니
    건드리지 않는다.
  - **마일스톤** — 이 이슈에 있으면 `--milestone "<이름>"` 으로 맞춘다.
    **이슈에 없으면 손대지 않되, PR에 붙어 있으면 그 사실을 최종 보고에 적는다** —
    "이슈 #<번호>에는 마일스톤이 없는데 PR #<번호>에는 `<이름>` 이 붙어 있다".
    라벨과 달리 `--remove-milestone` 으로 떼지 않는 이유는 1단계가 마일스톤은 사람과
    확인하지 않아서다 — 값만 봐서는 **이슈에서 뗀 것인지 사람이 PR에 직접 단 것인지
    구분할 수 없다.** 그렇다고 조용히 두면 릴리스 계획이 어긋난 채 남는다(마일스톤을
    닫을 때 그 버전에 안 나갈 작업이 목록에 들어 있게 된다). 어느 쪽인지 자동으로 정하지 않고 **보이게만
    한다** — 이 워크플로가 애매한 비가역 판단을 다루는 방식 그대로다.
- **`gh pr create`·`gh pr edit` 가 본문이 길다고 거부하면 멈추고 보고한다**(GitHub 본문 한도 65,536자 — PR 코멘트도
  같은 한도라 코멘트로 옮겨서는 풀리지 않는다). 상한 10회 안의 라운드 기록이 그만큼 길어질 일은 드물어(be PR #29 는
  11라운드를 싣고 3,463자였다) 줄이는 규칙을 따로 두지 않는다 — 어떻게 할지는 사람이 정한다. 싣지 못한 라운드는
  4단계대로 그 보고에 "PR 에 안 실린 라운드"로 밝힌다.
- 본문에 **개발자가 눈으로 확인해야 할 것**(API 응답·흐름)을 체크리스트로 명시한다 —
  자동 게이트가 어디까지였는지도 밝힌다 (수준은 CLAUDE.md 빌드 절의 기본 게이트
  기준을 그대로 옮긴다 — 여기 박아두면 게이트가 바뀔 때 낡은 진술이 된다).
- 4단계의 **라운드 기록**을 본문에 `<details>` 로 접어 싣는다(항목은 4단계 그대로). "가릴 수 없음" 후보는 위
  체크리스트에도 올린다 — 세션이 내린 판정을 팀원이 볼 수 있는 자리는 PR 이다.
  **라운드 기록 칸**은 라운드 기록을 접어 둔 `<details>` 칸이고, summary 에 그 칸이 담은 라운드 번호 범위를 적는다
  (예: `셀프 코드리뷰 라운드 기록(5~7/10)`). 이 규칙 전에 연 PR 은 summary 문구가 다를 수 있으니(`셀프 리뷰 기록`
  등) 내용으로 알아본다.
  갱신 갈래에서는 **기존 라운드 기록 칸은 고치지 않고**, 맨 뒤 기록 칸 다음에 새 칸 하나를 단다(기록 칸이 없으면
  본문 맨 끝에 단다). 새 칸에는 이번 실행의 라운드를 담고, 4단계가 붙여 받은 멈춤 보고를 앞 기록으로 골랐으면 그
  보고가 "PR 에 안 실린 라운드"로 밝힌 것도 함께 담는다 — PR 쪽을 골랐으면 보고에서 옮기지 않는다. 이미 본문에 있는
  라운드를 다시 싣지 않으려고 보고가 그 둘을 나눠 적는다(4단계). 체크리스트에는 새 항목만
  더하고, 이미 있는 항목과 사람이 체크한 칸은 고치지 않는다. 요약처럼 나머지 부분은 이번 변경에 맞게 고쳐 쓴다.
- 생성된 **PR 번호와 브랜치 이름을 최종 보고에 남긴다** — 머지 후처리(7단계)가
  이 기록으로 대상을 특정한다.

## 6. 종료

- PR URL·번호, 4단계의 라운드 기록, 개발자 확인 필요 항목을 보고하고
  **여기서 멈춘다.** 라벨·마일스톤과 잔재에서 **일부러 자동 처리하지 않았거나 사람이 모르게
  바뀐 것들도 여기 함께 적는다** — 지금은 1단계에서 "그대로 진행"으로 넘긴 라벨 어긋남,
  5단계 push 전에 다시 읽은 이슈 라벨이 1단계와 달라진 사실과 구현 뒤 달라진 area 판단, 5단계가
  PR에서 뺀 타입·area 라벨, 마일스톤 어긋남(이슈에 없는데 PR에 붙어 있는 경우), 2단계의
  `other-orphan` 줄, "시작하기 전에"가 작업 디렉터리를 옮긴 사실이 그것이다. 여기서 안 적으면 아무 데도 안 남는다. codex 리뷰 감시·반영은
  이 워크플로 범위 밖이다 — 사람이 리뷰를 보고 반영을 지시한다. 지시받아 반영할 때:
  - 그 사이 다른 이슈의 워크트리로 옮겨간 세션이면 **먼저 이 PR의 워크트리에 다시 들어간다.**
    레포 루트를 2단계와 같이 구하고 레코드를 찾는다(스냅숏 파일 자리는 `references/worktree.md`
    "먼저 알아 둘 것"):

    ```
    bash "<스킬 디렉터리>/scripts/find.sh" "<레포 루트>/scratchpad/wt-<평탄화한 브랜치명>.z" "<브랜치>"
    ```

    이 세션이 앞서 워크트리 제거 절차(2단계 잔재 정리·7단계)를 지났으면 `<스킬 디렉터리>` 가 그때 지운
    워크트리 안이었을 수 있다 — 그 절차 앞머리가 떠 둔 `<사본>` 으로 친다(`references/worktree.md`
    "워크트리 제거 절차"). 갈래는 이렇다:
    - `FOUND` 이고 블록에 `detached`·`locked`·`unsafe yes`·`unreadable yes`·`dangling yes`·`prunable`·
      `container out` 이 없으면 그 `path` 줄로 EnterWorktree(path:) 한다(이미 그 안에 서 있으면 그대로).
    - `detached`·`locked`·`unsafe yes`·`unreadable yes` 면 멈추고 보고한다. `dangling yes` 는 브랜치 ref 가
      지워진 등록이다 — **`prunable` 이 함께 있으면 아래 `prunable` 갈래로** 가고(등록을 치우고 재부착),
      디렉터리가 남아 있으면 `remove` 가 거부하므로 멈추고 보고한다.
    - `prunable` 이면 디렉터리가 사라진 등록이라 들어갈 수 없으니 `references/worktree.md` 이어받기 1번의
      `prunable` 갈래(등록만 치우고 재부착)를 따른다 — 제거 절차를 0번부터 돌리면 0번 ②가 이 PR 이 열려
      있다고 멈춘다. `container out` 이면 같은 문서 잔재 조사의 "답과 무관하게 지키는 것" 셋째 항목대로 한다.
    - `NONE` 이면 워크트리가 사라진 것이니 이어받기 1번의 재부착으로 간다. 그 밖의 키워드면 멈추고 출력을
      보여준다.

    (`git branch --list "<브랜치>" --format='%(worktreepath)'` 로 받지 않는다 — detached HEAD인
    워크트리에는 그 값이 안 붙어 빈 경로가 된다.)

    **들어갔으면(재부착했든 이미 서 있었든) 아래 순서로 확인하고 나서 고친다 — 순서를 바꾸지 않는다:**
    1. `git branch --show-current` 가 **그 PR의 브랜치인지 본다.** 아니면 멈추고 보고한다. 진입이 실패했거나
       건너뛰어졌는데 그대로 반영하면, 지금 서 있는 브랜치(다른 이슈의 워크트리이거나 본 체크아웃의 `main`)에
       커밋이 쌓이고 아래 push가 **그 브랜치의 PR에 이번 수정을 얹는다.** `--force` 를 쓰지 않으므로 되돌리는
       길은 revert 커밋뿐이다. 2단계 이어받기가 같은 이유로 두는 확인이다.
    2. `git fetch origin "refs/heads/<브랜치>"` — 원격 추적 ref 는 fetch 전에는 세션 시작 때 값이라, 받지 않으면
       3.이 "원격이 앞서 있음"을 못 본다(`refs/heads/` 는 같은 이름의 태그를 피하는 것 —
       `references/worktree.md` "먼저 알아 둘 것"). `couldn't find remote ref`(rc 128)면 원격에 그 브랜치가 없는 것이다
       (누가 지웠거나 아직 push 하지 않았다) — 3.의 ff-only 는 건너뛰고 그대로 간다. 그 상태로 ff-only 를
       치면 `not something we can merge`(rc 1)가 나오는데(실측) 그건 "갈렸다"가 아니다.
       위 2단계의 `bad object worktrees/<id>/HEAD` 갈래는 여기서도 같다 — 그 등록이 있으면 이 `fetch` 도
       죽는다(실측).
    3. `references/worktree.md` 이어받기 **3번**(`git status --porcelain` 이 비었는지)을 보고, 이어
       `git merge --ff-only "origin/<브랜치>"` 를 **조건 없이 친다**(이어받기 4번) — 여기에는 L·R 을 받아 둔
       자리가 없고, 최신이면 아무 일도 없으며 갈렸으면 실패하니 그때 묻는다. 그 사이 다른 세션이 그
       워크트리에서 편집 중이거나 GitHub 에서 리뷰 제안이 적용됐을 수 있고, 후자를 놓치면 아래 push 가
       non-fast-forward 로 거부되는데 여기에는 그 거부를 다루는 갈래가 없다. **1.보다 먼저 치지 않는다** —
       `main` 에 서 있을 때 ff 가 성공해 로컬 `main` 이 기능 브랜치 팁으로 전진한다(실측).
  - 지적이 틀렸다고 판단되면 자동 반박하지 않는다 — 근거를 정리해 사람에게
    판단을 넘긴다.
  - push 는 `git push -u origin HEAD` 로 친다 — 재부착이 `git fetch origin "refs/heads/<브랜치>:refs/heads/<브랜치>"`
    로 만든 브랜치에는 upstream 이 없어 맨 `git push` 가 거부된다(실측). 로컬 ref 가 없을 때 `git worktree add
    "<경로>" "<브랜치>"` 로 재부착하면 git 이 `origin/<브랜치>` 에서 DWIM 으로 만들며 upstream 을 붙이지만
    (실측. 같은 이름의 태그가 있으면 그 DWIM 은 태그로 풀려 브랜치 없이 detached 로 열린다 — 이것도 실측),
    어느 쪽이든 `-u` 를 붙여 치면 된다.
  - 반영 후 셀프 리뷰를 다시 돌릴 때는 반영 커밋을 **push한 뒤**
    **`/code-review high <PR번호>`** 로 PR을 직접 겨냥한다 — PR 타깃 리뷰는
    원격 diff를 읽으므로 push 전에 돌리면 낡은 코드를 리뷰한다. **범위 없는
    `/code-review high` 는 여기서 특히 안 된다** — 5단계의 `push -u` 가 upstream을
    `origin/<브랜치>` 로 걸어 두었으므로 기본 기준선 `@{upstream}...HEAD` 는 **빈
    diff**가 되고, 리뷰가 아무것도 안 보고 P1·P2 0건으로 통과한다.
  - **이 재리뷰도 4단계 루프 그대로다** — 분류·게이트(P1·P2 0건까지 반복)·안전장치·라운드 기록이 같고, 기록과 셈은
    4단계 "한 줄로 잇는다"대로 앞 기록에 잇는다. 다른 것은 위 범위(PR 번호)와, 반영 커밋을 push 한 뒤 돌린다는
    것뿐이다. 라운드마다 push 하므로 그 push 가 non-fast-forward 로 거부되면 5단계 push 항목의 그 갈래대로 한다(받아서
    ff 로 잇고, 안 되면 묻는다 — ff 로 붙인 커밋은 다음 라운드가 PR 을 겨냥해 함께 본다). 루프를 마치면(게이트가
    닫혔든 멈췄든) 보고하기 전에 5단계 본문 파일·라운드 기록 항목의 갱신 갈래대로 이번 루프의 라운드를 새 기록 칸으로
    더해 `gh pr edit <번호> --body-file <파일>` 로 PR 본문을 갱신한다(파일 자리와 지우기, 본문 길이로 거부될 때도
    5단계대로).

## 7. 머지 후처리

**"머지했어"를 받았으면 `references/merge-cleanup.md` 를 Read 하고 그대로 따른다.**
1~6단계는 건너뛴다. 머지는 사람이 하고, 거기서는 확인과 정리만 한다.

## 이 스킬을 고칠 때

- **ClimPick 사본들(limbing-ios·limbing-aos·climpick-ai)과 따로 관리한다 — 맞춰 고칠 의무가 없다.** 이 사본은
  limbing-aos `.claude/skills/issue` 를 옮겨 와(2026-10-27) 이 레포에 맞춘 것이고, 그 사본은 limbing-ios 것을 옮겨
  왔다(aos #43 — climpick-ai 사본도 같은 식으로 옮겨 갔다, ai #31). ClimPick 사본들은 서로 맞춰 고치지만 이 사본은 그
  묶음에 들지 않는다 — 여기를 고쳐도 그쪽에 옮기지 않고, 그쪽이 바뀌어도 여기로 옮겨 올 의무가 없다. 그쪽 개선을
  가져오고 싶으면 파일째 옮기지 않고 diff 로, 고친 뜻을 보고 골라 옮긴다 — 레포 사정을 바꾼 문장이 곳곳에 있다(첫머리,
  "어느 레포 작업인지"의 레포 이름, 1단계의 라벨 개수, 3단계(limbing-aos 의 `local.properties` 준비를 걷어 냈다), 4단계
  리뷰 상한(숫자는 ClimPick 사본과 같은 10회지만 근거 문장이 다르다 — be #21)과 4단계의 센 라운드·완결 라운드·라운드
  기록(be #26), 그 기록을 잇는 자리(4단계 "한 줄로 잇는다"·5단계 PR 확인과 본문 파일의 순서와 갱신 갈래·6단계 재리뷰 — be #28),
  `ignored-check.sh` 의 판정, references 워크트리 제거 2번·3번).
  옮겨 올 때 알아 둘 것: `orphan-check.sh` 는 limbing-aos·climpick-ai 사본과 판정이 같고 limbing-ios 사본과
  다르다(그쪽만 Xcode 흔적 판정 `XCODE_ONLY`·`TOO_MANY`·걷기 상한이 있다). references 워크트리 제거 2번(도는 작업
  멈추기)은 사본마다 다르다 — limbing-ios 는 Xcode 문서를 닫고, limbing-aos 는 Gradle 빌드를 멈춰도 되는 근거와
  Android Studio 창 확인이 있고, 이 사본은 그 Gradle 근거를 두고 창 확인을 IntelliJ IDEA 로 바꿨으며, climpick-ai 는
  둘 다 없다. 그러니 2번은 diff 로도 옮기지 말고 고친 뜻만 옮긴다. `ignored-check.sh` 는 limbing-aos 사본(그쪽은
  climpick-ai 사본에서 옮겨 왔다)에서 옮겨 와 "다시 만들 수 있는 것" 판정(`regenerable` 과 `.idea` 안 폴더 확인)을
  이 레포에 맞췄고(스크립트 머리말), limbing-ios 에는 없다. `.DS_Store` 판정은 `orphan-check.sh` 와 따로 적혀
  있다 — ClimPick 사본들이 똑같이 두는 `lib.sh` 로 옮기면 한 사본만 고칠 수 없어서다(이 사본의 `lib.sh` 도 옮겨 올
  때 그쪽과 같았다). `volume-check.sh` 는 climpick-ai 에만 있다. 그 밖의 판정 스크립트의 판정 코드는 옮겨 올 때
  limbing-aos 사본과 같았다(ios #562 에서 두 사본을 맞췄고, limbing-aos 는 그 뒤 limbing-ios 것을 옮겼다).
- **판정은 스크립트에, 무엇을 왜 하는지와 키워드별 갈래는 문서에** 둔다. 판정 규칙을 산문으로
  적으면 같은 규칙이 여러 곳에 생기고 한 곳만 고쳐져 나머지가 낡는다(ios #287·ios #322에서 반복됐다).
  스크립트를 고치면 `tests/run.sh` 에 그 경우를 더한다. 테스트는 스크립트가 내는 키워드가 문서에
  다 적혀 있는지, 문서가 부르는 스크립트가 다 있는지도 본다.
- **문서에 적는 명령은 실행한 것을 문자 그대로 옮긴다.** "실행해 본다"로는 안 걸린다 — 비슷한
  명령을 돌려 보고 변형해 적은 것이 실패의 대부분이었다(`grep -m1 '^worktree '` 가 접두어까지 낸다,
  `for-each-ref` 포맷에서 `%(objectname)` 을 빠뜨렸다, `find` 가 검색 루트 자신을 낸다, 삭제된 cwd
  에서 조상 순회가 끝나지 않는다).
- **이 파일(SKILL.md) 본문에는 달러 기호 바로 뒤에 숫자나 ARGUMENTS 를 붙여 쓰지 않는다.** 스킬을
  부를 때 Claude Code 가 그 자리를 인자로 치환한다(체인지로그 2.1.19). 옛 문서의 awk 유일성 카운터에 있던
  레코드 변수가 `/issue 319` 로 부르자 `319` 로 바뀌어, 카운터가 망가진 채로 실렸다(2026-09-11 실측).
  받을 인자가 없는 자리는 그대로 남으므로(2.1.210) 같은 줄이 인자 개수에 따라 다르게 망가진다. 백슬래시
  이스케이프가 있지만(2.1.163) 판정 코드는 이 파일에 적지 말고 scripts 에 둔다. references 와 scripts 는
  Read 로 읽거나 실행하므로 이 치환을 거치지 않는다. `tests/run.sh` 가 이 파일을 검사한다.
- 비가역 명령(`worktree remove`·`branch -D`·`push --delete`·`rm -rf`·`worktree prune`)의 동작을 새로
  적을 때는 임시 레포에서 확인하고 테스트로 남긴다 — 실행할 기회가 드물어 리뷰로는 안 걸린다.
